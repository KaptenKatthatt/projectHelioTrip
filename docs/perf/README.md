# Performance baselines

Generated by `npm run perf:baseline` (`scripts/perf-baseline.mjs`).

## The `baseline-20260428-*` files are invalid — do not compare against them

Every baseline captured on 2026-04-28 profiled `http://localhost:5173`, i.e. the
Vite **dev server**: unminified React with dev-only warnings, the HMR client, no
tree shaking, and a per-module network waterfall. They read ~1.2 FPS with 98% of
CPU samples in `(program)`. Those numbers describe Vite's dev pipeline, not the
app, and no conclusion about rendering performance can be drawn from them.

They are kept only so the mistake is visible in history. Treat the first run
produced by the current script as the real baseline.

## Capturing a comparable run

The script serves `dist/` itself via `vite preview`, so build first:

```sh
npm run build
npm run perf:baseline
```

Always pin the quality level. Without `PERF_QUALITY` the adaptive controller is
what gets measured, and no two runs are comparable:

```sh
PERF_QUALITY=0 npm run perf:baseline
```

To measure a weak GPU reproducibly on any machine, render through SwiftShader:

```sh
PERF_SOFTWARE=1 PERF_QUALITY=4 npm run perf:baseline
```

Other knobs: `PERF_BASE_URL` (profile an already-running server instead of
spawning one), `PERF_SAMPLE_MS`, `PERF_WARMUP_MS`, `PERF_HEADLESS`.

## Reading the output

`p50FrameMs` and `p90FrameMs` are the numbers to watch — they are what the
runtime adaptive-quality controller reasons about, so harness output and
controller decisions stay in the same units. Average FPS hides sustained
stutter: a scene alternating 8 ms and 40 ms frames has a respectable average and
feels awful.
